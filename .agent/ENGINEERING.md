# Shiftory 工程约束

本文记录开发时需要遵守的边界。产品目标见 [产品需求](REQUIREMENTS.md)，启动与部署步骤见 [README](../README.md)。需求、接口契约和代码存在差异时，应核对具体调用链，不能把需求中的目标当成已实现行为。

## 模块与错误边界

- 后端按业务模块组织；`internal/platform/httpserver` 负责 HTTP 适配、权限检查与响应序列化，`importer`、`schedule` 等领域包不依赖 Gin。
- 数据访问使用 `database/sql` 与参数化 SQL，表结构由 `internal/platform/database/models.go` 的 GORM 模型维护。认证、导入任务使用 Repository；部分业务查询仍位于 HTTP 路由文件中，不能假定所有模块已完成统一的三层拆分。
- 工作簿规范化返回 `ValidationError`，保留行号、字段、规则码、修复提示和底层错误链。HTTP 层映射为 `INVALID_WORKBOOK`，通过 `error.details` 暴露 `row`、`fields`、`ruleCode`、`hint`，不直接暴露内部堆栈或 SQL。
- 前端导入错误应展示行号、字段和修复提示，最终校验与授权仍由后端负责。

- 数据库使用 UTF8 编码，本机共享实例使用 C locale；字符串比较区分大小写和重音，应用层继续规范化业务键。绝对时间使用 timestamptz 并固定 UTC 会话时区，排班日期及班次时刻分别使用 date 和 time。updated_at 由数据库触发器维护。

## 排班与导入一致性

- GORM 模型定义正式日排班按 `(user_id, work_date)` 唯一。工作区用于授权、班次映射及导入上下文，不能据此建立同一用户同一天的另一份正式排班。
- 项目处于开发阶段，尚未部署。API 启动时执行 GORM AutoMigrate，不再执行版本化 SQL 或数据清空迁移；自动迁移不负责删除废弃列、重命名字段或清理旧约束。初始化 SQL 仅用于空库，默认开发账号不会由 API 自动创建。
- 排班保存班次快照；修改班次定义不能反向改变已保存排班。跨日归属开始日期，缺失记录不等于休息。
- 导入预览保留原排班 ID 和版本；提交时重新核对并在一个事务中写入选中的排班、修订和任务状态。导入撤销检查写入后的版本与来源，拒绝覆盖后续修改。
- 图片识别只生成草稿，经领域校验、班次映射和人工确认后才能写入正式排班。不确定项不能自动写入。
- 原文件通过存储接口访问。文件写入与 PostgreSQL 事务不是同一事务，数据库提交失败后的文件删除属于补偿操作。

- 解散工作区保留个人排班和修订，通过可空外键解除工作区、班次、导入的来源引用；展示快照不依赖班次定义继续存在。
- 邀请不能覆盖有效或禁用成员的角色；管理员邀请只能由所有者发出，接受时复核邀请人的权限。导入提交和撤销在事务内锁定操作者及目标成员，检查当前写权限。
- 前端注销清空查询缓存；全局排班变更使所有工作区的排班、日历、统计和历史缓存失效。团队导入详情使用显式只读路由，导入链接携带工作区 ID。

## AI 任务运行

- API 是唯一长期运行入口；启动完成结构同步和 Eino Workflow 编译后开放 HTTP。AI 启用时启动 Asynq 消费器及 Outbox Dispatcher，不另加协程池。
- PostgreSQL 保存业务任务、事务 Outbox、输入快照、轮次与模型诊断；Redis 保存 Asynq 消息和共享供应商并发／熔断状态。
- 投递及执行允许重复，写入检查 generation、随机执行 token、状态与租约期限。取消释放执行权，旧结果不得回写。
- 整轮按模型优先级有限切换，Asynq 控制重试；没有实际模型请求的供应商等待不消耗模型轮次。归档或消息丢失后的任务转失败，人工重试创建新 generation。
- 正常停机停止 Dispatcher 和新领取，有界等待运行任务，然后关闭连接。Redis 极端数据丢失不自动重建；历史图片任务只通过显式 `--migrate-ai-jobs` 接纳。

## 配置、日志与部署

- API 与 migrate 共用 `--env` 和 `--config`，默认生产模式；非空进程环境变量优先于 YAML，其次使用内置默认值。后端不加载 env 文件，前端继续使用 Vite 的 `.env*` 与 `VITE_*`。
- 后端 YAML 按 log、server、postgres、jwt、ai、redis、tasks、storage 分组；worker 仅保留旧字段兼容，环境变量采用 SHIFTORY_<分组>_<字段>。server.port 指定监听端口；postgres 使用 host、port、database、user、password、sslmode，连接串统一编码，会话时区固定 UTC。不接受运行时 DSN 或平铺 YAML 键。
- 未显式指定配置时，按工作目录、父目录、祖父目录查找首个 `config/<模式>.yaml`；文件不合并。显式路径缺失、非法 YAML、未知键或非法值会报错。相对路径以进程工作目录为基准。
- 样例配置只保存可分发值；实际 YAML、JWT 私钥、模型密钥与上传文件不能进入版本控制。生产部署需要持久化上传目录与 JWT 密钥。
- 开发日志默认 `debug` 与文本格式，生产默认 `info` 与 JSON；支持显式覆盖。请求日志包含请求 ID、路径、状态和耗时，不记录令牌、API Key 或图片内容。
- PowerShell 开发启动器可预先同步表结构，再启动 API 与前端；API 自身也会执行同步。`-ValidateOnly` 检查工具和配置路径，不能替代 Go 加载器的配置校验。
- Linux 启动脚本透传模式与配置参数；systemd 使用显式 YAML 路径。Docker 入口先迁移再启动 API，Compose 使用 `COMPOSE_DISABLE_ENV_FILE=1` 避免额外隐式加载根目录 env 文件。

## 成员邀请与前端约定

- 邀请请求的邮箱和用户名二选一。用户名必须对应有效用户，由后端解析为规范化邮箱；邮箱模式保留令牌邀请和接受流程。
- Pinia 管理用户、工作区与主题等界面状态，服务端业务数据由请求层负责刷新。当前工作区不是后端鉴权依据，认证令牌不能持久化到浏览器存储。
- 导入确认框采用中文“确认／取消”，展示六类导入结果的说明。状态与分类可显示小写，API 枚举和业务判断保持原值。
- 六套浅色主题应同时影响侧边栏、导航选中态和主内容区域，语义颜色保持稳定。

## 实现边界与验证

- 模块范围见 [DATA_SCOPES.md](DATA_SCOPES.md)。个人排班通过认证身份访问 `/me/schedules`，无需工作区；预设班次需验证显式来源的成员关系。个人页面不因工作区切换重建，顶部切换器只用于工作区页面。
- 手动、Excel 和图片预览均按用户与日期读取全局排班；工作区排班查询必须先验证目标成员关系，并沿用日历的离开日期可见边界。
- `internal/platform/httpserver/calendar_routes.go` 对未离开的成员允许展示其既有排班，离开成员按离开日期截断；未指定成员时纳入全部现有成员及关系与查询区间相交的历史成员。前端空选表示默认范围，不能禁用查询。不能将其描述为对每一天都严格应用加入、离开区间。
- 产品需求中的功能清单是验收范围。判断前端完成度需检查实际源码和构建输入；不能沿用历史计划中的完成标记或旧测试结果。
- 后端执行 `go test ./... -count=1`、`go vet ./...`；数据库集成测试需要PostgreSQL 18 和隔离的测试数据库。前端需分别验证测试、类型检查和生产构建。
- PowerShell 架构、开发工具和 GoLand 检查见 `scripts/tests/`。真实图片模型识别、数据库任务恢复和部署运行需要相应运行环境，静态检查不能代替这些验收。
