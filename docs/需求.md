# 排班协同平台需求与技术选型确认稿

版本：v0.2
状态：核心需求确认中
项目形态：Go + Vue 3 前后端分离、模块化单体

---

## 一、项目定位

本项目是一个面向个人与团队的排班协同平台。

用户可以通过以下方式导入自己的排班：

1. 上传排班表截图，由 AI 识别；
2. 上传 Excel 文件，由系统按照排班模板解析；
3. 在系统内手动新增或修改排班。

系统将不同来源、不同表达方式的排班数据统一为标准结构，并在工作区内提供个人排班查看、团队排班查看、休息人员统计以及共同休息日计算功能。

项目的核心能力不是简单保存 Excel 文件，而是：

* 将截图和 Excel 转换为统一排班数据；
* 支持工作、休息、早中晚班和时间段等不同排班表达；
* 支持按照指定成员范围计算每天谁上班、谁休息；
* 在全部选中成员都休息时进行特殊标记；
* 通过人工确认避免 AI 或 Excel 导入错误覆盖现有数据。

## 二、核心业务概念

### 2.1 用户

用户是系统的登录账号。

一个用户可以加入多个工作区，在不同工作区中拥有不同角色。

例如：

```text
用户 A
├── 工作区 1：管理员
├── 工作区 2：普通成员
└── 工作区 3：普通成员
```

---

### 2.2 工作区

工作区是排班数据的隔离边界。

每个工作区独立维护：

* 工作区成员；
* 成员角色；
* 班次定义；
* 排班数据；
* 导入记录；
* 工作区设置。

用户登录后，顶部导航栏显示工作区切换器。

当前暂按以下方式定义：

> 用户可以加入多个工作区，但同一时间只激活一个当前工作区。

进入我的排班、团队日历、成员管理等页面时，所有数据都属于当前工作区。

当前工作区只属于前端 Pinia 中的界面状态和用户偏好，不能作为后端权限依据。工作区业务 API 必须通过 `/api/v1/workspaces/{workspaceId}/...` 显式携带工作区 ID，后端对每次请求重新检查当前成员关系。

每个工作区必须设置 IANA 时区，例如 `Asia/Shanghai`。排班日期和班次时间按照工作区时区解释；`created_at`、`updated_at`、任务租约和审计时间统一使用 UTC 保存。

首版不实现多个工作区数据同时聚合，也不实现跨工作区共同休息日计算。

---

### 2.3 工作区角色

产品主要面向两类角色：

* 管理员；
* 普通成员。

数据库层建议额外保留工作区所有者 `OWNER`，用于处理工作区转让、管理员设置和工作区删除等特殊操作。

角色定义为：

```text
OWNER  工作区所有者
ADMIN  工作区管理员
MEMBER 普通成员
```

在大部分业务页面中，`OWNER` 与 `ADMIN` 的使用体验基本一致。

工作区成员关系需要保留 `status`、`joined_at` 和 `left_at`。禁用或移除成员只终止其当前访问权限，不删除历史排班、导入记录和审计记录。历史日期统计按照成员关系的有效时间范围判断可选成员。

---

## 三、权限模型

管理员和普通成员使用同一套前端系统、同一套页面布局和同一套基础组件，不创建独立的“用户端”和“管理后台”。

不同角色之间的差异主要体现在：

* 可见菜单数量；
* 页面中的操作按钮；
* 可选择的目标用户范围；
* 后端接口权限。

### 3.1 权限矩阵

| 功能             | 普通成员 | 管理员 | 所有者 |
| -------------- | ---: | --: | --: |
| 查看自己的排班        |    是 |   是 |   是 |
| 编辑自己的排班        |    是 |   是 |   是 |
| 导入自己的排班        |    是 |   是 |   是 |
| 查看工作区内所有人的最终排班 |    是 |   是 |   是 |
| 查看所有人的班次和时间段   |    是 |   是 |   是 |
| 查看团队日历         |    是 |   是 |   是 |
| 查看共同休息日        |    是 |   是 |   是 |
| 编辑其他成员的排班      |    否 |   是 |   是 |
| 替其他成员导入排班      |    否 |   是 |   是 |
| 管理班次           |    否 |   是 |   是 |
| 邀请和移除成员        |    否 |   是 |   是 |
| 设置成员角色         |    否 |  受限 |   是 |
| 查看全部导入任务       |    否 |   是 |   是 |
| 修改工作区设置        |    否 |   是 |   是 |
| 转让或删除工作区       |    否 |   否 |   是 |

普通成员可以看到其他成员的完整、已确认排班信息，但不能修改其他成员的数据。

这里所说的完整排班信息包括：

* 工作或休息状态；
* 班次名称；
* 开始时间和结束时间；
* 是否跨日；
* 排班备注。

原始截图、原始 Excel 文件、AI 原始响应和导入错误信息不属于普通排班信息。首版默认只允许上传者本人和管理员查看这些导入资料。

## 四、菜单结构

### 4.1 所有成员共有菜单

```text
概览
我的排班
导入排班
团队日历
我的导入记录
个人资料
```

### 4.2 管理员额外菜单

```text
排班管理
成员管理
班次设置
全部导入记录
工作区设置
```

### 4.3 所有者额外能力

工作区所有者不一定需要单独菜单，可以在成员管理和工作区设置中增加：

* 设置或取消管理员；
* 转让工作区；
* 解散工作区。

前端根据当前角色动态生成菜单，但后端仍然必须进行完整权限校验，不能只依赖前端隐藏按钮。

## 五、排班数据模型

### 5.1 排班状态

首版只存在两种明确状态：

```text
WORKING 工作
REST    休息
```

系统不区分：

* 请假；
* 年假；
* 调休；
* 病假；
* 法定节假日；
* 周末休息；
* 其他休假类型。

所有不工作的情况统一记录为 `REST`。

系统也不会根据星期六、星期日或法定节假日自动判断休息。某一天是否休息，只取决于用户的实际排班数据。

---

### 5.2 未知状态

某个用户在某一天没有排班记录时，该日期应被视为：

```text
MISSING 数据缺失
```

`MISSING` 不作为正式排班状态写入数据库，而是在查询时根据记录是否存在动态计算。

必须严格区分：

* 明确休息；
* 没有上传或录入排班。

例如：

```text
选择 5 名成员
4 人明确休息
1 人没有排班数据
```

这一天不能判定为全部休息。

---

### 5.3 日排班记录

每个成员每天最多有一条日排班主记录。

建议实体：

```text
ScheduleDay
```

主要字段：

| 字段                 | 含义                 |
| ------------------ | ------------------ |
| `id`               | 排班记录 ID            |
| `workspace_id`     | 所属工作区              |
| `user_id`          | 排班所属用户             |
| `work_date`        | 排班日期               |
| `status`           | `WORKING` 或 `REST` |
| `source_type`      | 手动、Excel、图片 AI     |
| `source_import_id` | 对应导入批次             |
| `note`             | 排班备注               |
| `version`          | 乐观锁版本              |
| `created_by`       | 创建或导入人             |
| `created_at`       | 创建时间               |
| `updated_at`       | 更新时间               |

唯一约束：

```text
(workspace_id, user_id, work_date)
```

---

### 5.4 排班详情

工作日可以存在以下三种情况：

#### 只有工作状态

```text
2026-09-01
状态：工作
具体班次：未知
```

#### 使用预定义班次

```text
2026-09-02
状态：工作
班次：早班
```

#### 使用具体时间段

```text
2026-09-03
状态：工作
时间：08:30—17:30
```

---

### 5.5 多时间段支持

虽然绝大多数排班只有一个班次或一个时间段，但底层数据模型仍支持同一天多个时间段。

例如：

```text
08:30—12:00
13:30—17:30
```

建议使用独立实体：

```text
ScheduleSegment
```

主要字段：

| 字段                | 含义                     |
| ----------------- | ---------------------- |
| `schedule_day_id` | 对应日排班                  |
| `segment_type`    | `SHIFT` 或 `TIME_RANGE` |
| `shift_id`        | 使用预定义班次时填写             |
| `start_time`      | 自定义开始时间                |
| `end_time`        | 自定义结束时间                |
| `cross_day`       | 是否跨到次日                 |
| `sort_order`      | 多时间段排序                 |
| `original_label`  | 导入文件中的原始名称             |

使用预定义班次时，排班详情除保留 `shift_id` 外，还必须保存班次名称、开始时间、结束时间、跨日状态和展示颜色快照。管理员后续修改班次定义时，不得改变已经存在的历史排班展示和统计结果。

排班写入规则：

* `REST` 不允许包含任何时间段；
* `TIME_RANGE` 的开始和结束时间必须同时存在；
* 同一天多个时间段不能重叠；
* 跨日必须显式设置，且单个时间段最长不超过 24 小时；
* 跨日排班始终归属开始日期，不参与次日 `WORKING` 人数的重复计算。

前端默认只展示一个班次或时间段输入区域。

只有用户点击“添加时间段”后，才显示多个时间段编辑能力，避免因为少见场景让普通操作变复杂。

---

### 5.6 跨日支持

系统支持跨日班次，但跨日不是主要使用场景。

例如：

```text
2026-09-03 20:00
至
2026-09-04 08:00
```

该排班仍归属 `2026-09-03`，并通过：

```text
cross_day = true
```

明确表示结束时间属于次日。

系统不应仅根据“结束时间早于开始时间”自动推断跨日，导入预览和手动编辑时都应明确显示跨日状态。

---

## 六、班次设置

每个工作区可以维护自己的班次。

创建工作区时，可以预置：

```text
早班
中班
晚班
```

管理员可以修改或增加班次。

班次主要字段：

| 字段              | 含义              |
| --------------- | --------------- |
| `name`          | 班次名称，例如早班       |
| `code`          | 班次代码，例如 MORNING |
| `start_time`    | 开始时间，可为空        |
| `end_time`      | 结束时间，可为空        |
| `cross_day`     | 是否跨日            |
| `display_color` | 展示颜色            |
| `enabled`       | 是否启用            |
| `sort_order`    | 排序              |

班次时间允许为空。

例如某些排班表只标记“早班”，但没有明确规定早班的具体时间，系统仍然可以保存该班次。

### 6.1 班次别名

为了支持 Excel 和图片识别，每个班次可以配置多个别名：

```text
早班
├── 早
├── 早班
├── A
├── 白班
└── Morning
```

识别到别名后，系统将其转换为工作区内的标准班次。

无法映射的班次不能直接写入正式排班，需要在导入预览中提示用户选择对应班次。

## 七、Excel 导入

### 7.1 支持格式

首版支持：

```text
.xlsx
.xls
```

其中：

* `.xlsx` 是主要支持格式；
* `.xls` 是兼容格式；
* 两种格式使用相同的业务模板和校验规则。

Excelize 官方支持 `.xlsx`、`.xlsm` 等 Excel 2007 及之后的 OOXML 格式，但不直接支持旧版二进制 `.xls`，因此后端需要通过统一解析接口分别适配两种格式。旧版 `.xls` 可以接入只读解析器，解析完成后统一转换为内部行数据。

推荐后端抽象：

```go
type WorkbookReader interface {
    Read(ctx context.Context, file io.Reader) (*WorkbookData, error)
}
```

具体实现：

```text
XLSXReader：使用 Excelize
XLSReader：使用独立的旧版 XLS 只读解析器
```

这样业务层不需要关心上传文件的具体格式。

### 7.2 模板边界

当前仍按平台固定模板处理，不支持任意结构 Excel 自动映射。

推荐模板字段：

| 日期         | 状态 | 班次 | 开始时间  | 结束时间  | 是否跨日 | 备注 |
| ---------- | -- | -- | ----- | ----- | ---- | -- |
| 2026-09-01 | 工作 | 早班 |       |       | 否    |    |
| 2026-09-02 | 休息 |    |       |       | 否    |    |
| 2026-09-03 | 工作 |    | 08:30 | 17:30 | 否    |    |

一天存在多个时间段时，可以出现多行相同日期。

### 7.3 Excel 校验规则

* 日期必须能够解析；
* 状态只能是工作或休息；
* 休息日不能包含班次或时间段；
* 工作日允许不填写具体班次；
* 班次必须能映射到工作区班次；
* 开始时间和结束时间必须同时填写；
* 是否跨日必须明确；
* 同一日期出现多行时，合并为多个时间段；
* 不执行宏；
* 不执行上传文件中的脚本；
* 不依赖公式动态计算；
* 加密或损坏文件直接拒绝；
* 文件扩展名和实际文件格式必须同时校验。

由于 `.xls` 属于兼容能力，应设置比 `.xlsx` 更严格的：

* 文件大小限制；
* 工作表数量限制；
* 行列数量限制；
* 解析超时；
* 异常恢复。

## 八、图片 AI 导入

### 8.1 图片范围

一张图片只对应一个成员的排班，不支持一张图片同时识别多名成员。

普通成员上传时，目标成员固定为自己。

管理员上传时，可以选择工作区内任意成员作为目标成员。

### 8.2 上传时需要的信息

用户上传图片时需要提供：

* 目标成员；
* 排班年份；
* 排班月份或明确日期范围；
* 排班截图；
* 可选识别说明；
* 可选班次映射提示。

目标成员不能由 AI 自行推断。

年份和月份在图片中明确存在时，系统可以自动提取，但仍应在预览页面展示并允许用户修改。

### 8.3 AI 技术边界

图片识别模块使用 tRPC-Agent-Go 组织模型调用和处理流程。

AI 的职责是：

* 理解表格结构；
* 提取日期；
* 提取工作或休息状态；
* 提取班次名称；
* 提取时间段；
* 标记不确定内容；
* 输出结构化草稿。

AI 不具备以下权限：

* 直接写入正式排班表；
* 自动覆盖现有排班；
* 删除原排班；
* 自行选择目标用户；
* 跳过人工确认；
* 修改工作区班次设置。

### 8.4 AI 识别流程

```text
上传图片
    ↓
保存原始文件
    ↓
创建导入任务
    ↓
图片尺寸与格式检查
    ↓
必要的压缩和方向纠正
    ↓
调用视觉模型
    ↓
获得结构化 JSON
    ↓
Go 业务规则校验
    ↓
班次别名映射
    ↓
生成导入预览
    ↓
用户修改并确认
    ↓
写入正式排班
```

AI 输出示例：

```json
{
  "period": {
    "start": "2026-09-01",
    "end": "2026-09-30"
  },
  "entries": [
    {
      "date": "2026-09-01",
      "status": "WORKING",
      "segments": [
        {
          "type": "SHIFT",
          "originalLabel": "早",
          "mappedShiftCode": "MORNING"
        }
      ],
      "uncertain": false
    },
    {
      "date": "2026-09-02",
      "status": "REST",
      "segments": [],
      "uncertain": false
    }
  ]
}
```

## 九、导入任务

Excel 导入和图片识别统一使用导入任务模型：

```text
ImportJob
```

任务状态：

```text
UPLOADED       已上传
PENDING        等待处理
PARSING        解析中
NEEDS_REVIEW   等待用户确认
COMMITTING     正在提交
COMPLETED      已完成
FAILED         失败
CANCELLED      已取消
ROLLED_BACK    已撤销
```

图片 AI 识别必须异步执行。

首版使用：

```text
MySQL import_jobs 表
+
Go 单体服务内部 Worker
```

不引入 Redis 和消息队列。

前端可以每隔一段时间轮询任务状态。首版没有必要为了低频导入任务单独实现 WebSocket。

任务领取和恢复规则：

* Worker 使用数据库行锁领取任务，同一任务同一时间只能有一个 Worker 处理；
* 任务保存 `attempt_count`、`lease_owner`、`lease_expires_at`、`heartbeat_at` 和 `idempotency_key`；
* Worker 处理期间定期续租，租约过期的任务可以被其他 Worker 恢复；
* 可重试错误采用有限次数退避重试，校验错误直接进入 `FAILED`；
* 提交和撤销操作都必须支持幂等，重复请求不能重复生成排班或审计记录。

## 十、导入预览

所有导入都必须经过预览，不能上传后直接覆盖数据库。

导入结果分为：

| 类型  | 含义              |
| --- | --------------- |
| 新增  | 原来没有该日期记录       |
| 一致  | 与现有排班完全相同       |
| 冲突  | 与现有排班不同         |
| 无效  | 日期、班次或时间格式错误    |
| 不确定 | AI 无法可靠判断       |
| 缺失  | 目标日期范围内没有识别到该日期 |

### 10.1 冲突定义

同一工作区、同一成员、同一日期已经存在正式排班，并且新数据与原数据不一致时，判定为冲突。

以下变化都属于冲突：

* 工作变为休息；
* 休息变为工作；
* 班次变化；
* 时间段变化；
* 跨日状态变化；
* 时间段数量变化。

### 10.2 冲突处理

所有冲突都必须由用户明确选择：

```text
保留原排班
使用新排班
暂不导入该日期
```

系统不能默认覆盖，也不能在用户未处理完冲突时提交导入。

可以提供批量操作，例如：

```text
所有冲突均保留原数据
所有冲突均使用新数据
```

但该操作仍然属于用户主动确认，执行前需要二次确认。

### 10.3 提交前重新校验

导入预览生成后，其他人可能已经修改了排班。

因此正式提交时，后端需要再次检查排班版本。

如果正式数据在预览后发生变化，应重新产生冲突，而不是按照旧预览覆盖最新数据。

预览项必须记录生成预览时的排班 ID 和版本；对于当时不存在的日期，正式提交时仍需依赖唯一约束防止并发插入。排班内容比较使用规范化后的状态、班次快照、时间段、跨日状态和备注，不比较导入批次等来源元数据。

### 10.4 事务与撤销

一次导入中最终选中的排班，应当在一个数据库事务中提交。

系统需要记录：

* 导入前数据；
* 导入后数据；
* 导入人；
* 目标成员；
* 原始文件；
* AI 原始结果；
* 用户修改结果；
* 冲突决策。

管理员或导入人可以撤销一次已完成的导入。

撤销时同样需要检查当前数据是否又被其他操作修改，避免撤销动作覆盖更新后的排班。

一次导入的撤销采用全有或全无语义。只要任意受影响排班在导入完成后又被修改，整次撤销必须拒绝并返回冲突明细；系统不进行静默的部分撤销。排班历史使用结构化 `schedule_revisions` 保存，不能仅依赖通用审计日志恢复数据。

## 十一、团队日历与日期统计

### 11.1 查询条件


### 11.2 日期计算规则

对于日期 `d` 和成员集合 `S`：

```text
工作成员：
在 d 日期存在 WORKING 记录的成员

休息成员：
在 d 日期存在 REST 记录的成员

缺失成员：

```

全部休息的判断条件：

```text

并且
休息成员数量 = 选中成员数量
并且
缺失成员数量 = 0
```

```text

```

```text
9 月 18 日

全部休息
5 / 5
```

并使用柔和红色背景、红色边框或醒目标记。

| 成员 | 状态 | 班次或时间       |
| -- | -- | ----------- |
| 张三 | 休息 | —           |
| 李四 | 工作 | 早班          |
| 王五 | 工作 | 08:30—17:30 |
| 赵六 | 缺失 | —           |

由于普通成员可以查看工作区内其他成员的完整排班，详情抽屉对普通成员和管理员都开放。

### 11.4 不保存静态汇总结果

“谁休息”和“是否全部休息”依赖用户当前选择的成员范围，因此首版不创建静态的日期汇总表。

### 14.4 认证

采用 Access JWT + Refresh JWT：

* Access Token 使用短期 JWT，默认有效期 15 分钟；
* 前端只在内存中保存 Access Token，并通过 `Authorization: Bearer <token>` 发送；
* Refresh Token 使用可轮换的长期 JWT，默认有效期 7 天；
* Refresh Token 仅通过 `HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/api/v1/auth` Cookie 传输；
* 每次刷新都轮换 Refresh Token；服务端在 MySQL 中保存令牌族和令牌哈希，用于注销、主动撤销和重放检测；
* JWT 使用非对称签名并携带 `kid`，服务端校验签名算法、`iss`、`aud`、`exp`、`nbf` 和令牌类型；
* Access Token 只保存稳定的用户身份与令牌标识，不保存工作区角色和权限；每次访问工作区资源时，后端根据当前成员关系重新鉴权；
* 登录、刷新、修改密码、账号禁用和高风险操作需要记录安全审计；
* Refresh 和注销接口需要校验 `Origin` / `Referer`，并配置 CSRF 防护；
* 密码使用 Argon2id 哈希，禁止明文或可逆加密保存。

前端和后端生产环境通过同一个域名提供服务：

```text
/       Vue 静态页面
/api    Gin API
```

任何 Access Token、Refresh Token 或其他认证凭据都不得持久化到 `localStorage`、`sessionStorage` 或 Pinia 持久化插件中。

6. 只区分工作和休息；

8. 首版仅实现浅色模式和六套纯色主题；
9. 管理员可以替成员导入排班；
10. 用户可以加入多个工作区；
11. 顶部提供当前工作区切换器；
12. 管理员和普通成员使用同一套系统；
13. 角色差异主要通过菜单和操作权限体现；
14. 数据缺失不能被视为休息；
15. 全部休息结果根据当前选择的成员动态计算。
16. 认证采用短期 Access JWT 与可轮换 Refresh JWT，前端不持久化认证令牌，工作区权限由后端按当前成员关系实时校验。
